These examples come from a CLI that writes three captures through one trace store (`trace.store.*`), routed per environment. `Settings.Resolve` gives an environment whose cache has a valkey L2 the kv backend, and one without it `records.sqlite`. Each capture's kind is declared to match how its source behaves:

| Capture | Kind | Declared as | Why |
| --- | --- | --- | --- |
| SQL Server extended events | `sql_xevent` | unkeyed, `RetainStream` | One bounded stream per trace span. Every polled event is appended, so a re-sent buffer is stored twice. |
| SQL Server deadlocks | `sql_deadlock` | key `id`, `RetainRows` | One stream per environment accumulates across syncs that deliberately re-read an overlapping window. |
| JVM probe watches and traces | `jvm_trace` | key `id`, `RetainStream` | One stream per probe generation. A restarted follower replays the agent ring it already stored. |

To pick a declaration, ask two questions about the source:

1. **Can the same row arrive twice?** If so, give it a stable id and declare `KeyColumn`. Re-reads then become idempotent.
2. **Does the stream end?** A bounded capture keeps its stream whole (`RetainStream`) and seals it when done. A stream that accumulates forever ages out row by row (`RetainRows`).

A caveat: `EventStore.Since` returns the whole buffer when its cursor key is not found, and an unkeyed stream stores that re-append twice in either backend. Carrying `xetrace.Event.Sequence` on the row as `KeyColumn` would let both backends skip it.

## SQL Server deadlocks

### Capture → recordstore

A sync scans the newest stored rows for the latest timestamp, loads deadlock reports from a little before it, and appends them with `AppendTyped`. The overlap is harmless because `id` is the key. In `records.sqlite`, a re-read report is skipped inside the append transaction. In kv, one read of the batch's `row/<id>` keys happens before anything is written.

<div class="facet-diagram not-content" role="img" aria-label="deadlocks.Sync: keyed, row-retained sql_deadlock stream per environment in records.sqlite or kv">
  <SQLDeadlocksCapture client:load />
</div>

One stream per environment accumulates for as long as anything syncs it, so the kind is keyed (the overlap is harmless) and ages out row by row.

### sqlite vs valkey

<div class="facet-diagram not-content" role="img" aria-label="sql_deadlock in each backend: sqlite compared with valkey">

</div>

Retention is declared per kind, so a trace span's uuid stream of `sql_deadlock` rows also ages out row by row rather than expiring whole.

## JVM probe watches and traces

### Capture → recordstore

The follower is a [probe](../probes/): one exclusive writer per probe identity, draining the agent's ring by cursor and sealing the stream when stopped.

<div class="facet-diagram not-content" role="img" aria-label="ProbeFollower: keyed jvm_trace stream per probe generation in records.sqlite or kv">

</div>

A call's id is unique only within one opening of a probe, so every stream holds one generation: a span mints a uuid stream, and serve's follower names it by the generation.
